europrocessorv4.9.3

ESP32-S3 기반 아날로그 필름 현상용 로터리 프로세서 제어 펌웨어 전체 설명서. 스테퍼 모터로 현상 탱크를 정/역 교반하고, 약품 온도를 측정하며, 웹 UI와 물리 디스플레이(TFT + 로터리 인코더)로 레시피/수동 운전을 제어한다. 단일 .ino 모놀리식에서 PlatformIO 기반 C++ OOP로 이관(v4.0)된 구조 기준. v4.4~v4.8.1에서 안정성 전수 개선(PCNT 패닉 근본 수정·노이즈 가드·운전 중 플래시 차단), 웹 OTA, 멀티 보드 제어, 보드별 핀 배치(칩 MAC 자동 선택), 무디스플레이·N8R2 지원, WiFi 검색, 온도 보정이 추가되었고, v4.9~v4.9.3에서 정전·리셋 복구, 하드웨어 감시(DIAG/VM), 기존 제어 화면 통합 동시 제어(자동 탐색), AP 이름 = 이름.local 접속이 추가되었다. 현존 이슈·실측 기록은 ISSUES.md.

개요

이 펌웨어의 설계 목표는 세 가지다.

  • 모터 타이밍 보장 — 스텝 펄스는 하드웨어 ISR(FastAccelStepper)이 독립 생성하고, 상태머신은 Core 1에 격리되어 WiFi·웹·디스플레이 부하와 무관하게 정/역 교반 타이밍을 유지한다.
  • 크로스코어 안전성 — Core 0(웹/UI)은 모터·레시피 상태를 직접 건드리지 않는다. 모든 조작은 CommandQueue로 전달되어 Core 1 단일 코어에서만 상태가 바뀐다. 레이스를 구조적으로 제거.
  • 물리 손상 방지 — 부팅 즉시 모터 EN 차단·패널 핀 idle 고정, S-커브 감속(일시정지·단계 이동 포함), 운전 중 플래시 쓰기·재부팅 금지, 노이즈 가드, 연속 크래시 시 모터 잠금.
  • 펌웨어 하나로 여러 보드 — 핀 배치·화면 유무·온도센서 결선을 칩 MAC으로 자동 선택. 같은 사양이면 같은 .bin을 OTA.
읽는 순서. 하드웨어를 만지는 사람은 1~3·13장, 코드를 보는 사람은 4~9장, API를 쓰는 사람은 10장, 빌드·OTA는 12·15장, 여러 대 운용은 14장, 온도 정확도는 16장부터 보면 된다. 9장(크래시 분석)은 이 프로젝트에서 가장 비싸게 배운 교훈이라 따로 떼어 두었다.

속도 계산

출력축 RPM을 모터 step/s로 환산하는 식은 MotionController·Config.h에 동일하게 박혀 있다.

// step/s = 출력RPM × 기어비 / 60 × (200 step × 8 마이크로스텝)
MAX_SPEED = 80 RPM × 3.71 / 60 × 1600  ≈ 7,915 step/s
// S-커브 가감속 — 설정 RPM(v_t)까지 RAMP_SEC=2초, handover f=0.5
a   = v_t·(1+f)/T = 0.75·v_t        // 정가속 구간 가속도
s_h = f²·v_t·T / (1.5·(1+f)) ≈ 0.22·v_t  // 저크제한(소프트스타트) 스텝수
  • 출력 80RPM = 모터 약 297RPM = 7,915 step/s (MAX_SPEED 상한).
  • 80 초과 시 탈조는 코드 결함이 아니라 토크–속도 한계(back-EMF). 권장 운전 75RPM.
  • 하한 MIN_OUTPUT_RPM=5 — 실속(stall) 방지.

교반 시나리오

정방향 rotIntSec 구동→ 감속 정지→ REST 2초 (EN=HIGH, 코일 차단)→ 역방향 구동→ …

무한 반복. REST 구간(REST_MS=2000)에 TMC2209 EN을 HIGH로 올려 코일 전류를 끊어 관성을 안정시키고 발열을 억제한다. REST는 가속도 곡선 감속이 완전히 끝난 뒤 시작하므로 2초는 순수 휴식 구간이다. 레시피 모드에서는 각 단계가 속도 / 지속시간 / 방향전환주기를 개별로 가진다.

MotionController — 모터 상태머신

FastAccelStepper로 펄스를 생성하고 EN 핀은 수동 제어(REST 구간 코일 차단). 레시피를 모른다 — 단계 종료는 requestStepStop()으로 받고, 감속 완료는 takeStepStopped() 이벤트로 알린다. 모든 상태 변경은 Core 1에서만.

S-커브 가감속. beginRun()은 applyRamp(목표속도)를 호출해 설정 RPM마다 가속도와 저크제한 구간(setLinearAcceleration)을 다시 계산한다. 가속도가 0에서 선형으로 증가하는 소프트스타트라 출발/정지가 부드럽고, 어떤 설정 RPM이든 도달 시간이 RAMP_SEC(2초)로 일정하다. setLinearAcceleration은 stopMove() 감속에도 적용되어 정지도 대칭으로 부드럽다. (11장 상수)

API설명
beginRun(rpm,fwd)출력축 RPM·방향으로 구동 시작
stopImmediate()비상: forceStop + EN 차단 + IDLE (targetRpm=0)
requestSafeStop()가속도 곡선 감속 후 IDLE — 안전정지·일시정지·단계 이동이 모두 이 경로 (v4.6.1에서 즉시 정지 freeze() 삭제)
setLocked(on)노이즈 가드 모터 잠금 — beginRun() 단일 차단점에서 모든 기동 거부
requestStepStop() / takeStepStopped()레시피 단계 종료 감속 요청 / 완료 1회성 이벤트
state() · curRpm() · targetRpm() · isFwd() · cycle()상태 조회 (const)
초기화 시 PSRAM 점유. begin()은 FastAccelStepper 초기화 동안 PSRAM 여유 블록을 전부 잡아 PCNT 드라이버 객체가 내부 RAM에 할당되게 한다(9장).

RecipeRunner — 레시피 시퀀서

steps 벡터를 뮤텍스로 보호(웹 buildStatus가 Core 0에서 동시 읽기)하며, 모터는 MotionController 경유로만 구동한다.

load() → startStep(0) → 단계 지속시간 경과 시 requestStepStop()
       → 감속 완료(takeStepStopped) → waitConfirm(약품 교체 대기)
       → confirm() → 다음 단계 …

정전·리셋 복구. 진행 상태(단계 목록·현재 단계·경과·상태)를 NVS rec에 저장한다 — 모터가 멈춘 순간에만(단계 시작 직전, 확인대기, 일시정지 완료, REST 중 10초마다). begin()이 미완료 기록을 읽어 복구 대기(recoveryPending())로 두고, applyRecovery(RESUME|RESTART_STEP|NEXT_STEP|DISCARD)는 사용자가 고를 때만 실행(모터 IDLE 필수). 진행 중이었으면 남은 시간부터, 일시정지·확인대기였으면 그 상태로 복원. clear()는 이번 부팅에 쓴 기록만 지운다(수동 운전 시작이 이전 복구 기록을 지우지 않게). forcePause()는 하드웨어 고장 시 모터 동작 없이 일시정지로 보존.

그 외: pauseToggle()(감속 정지) · skipStep() / gotoStep(idx)(공통 switchTo() — 감속 정지 완료 후 목표 단계 시작) · snapshot()(표시용 상태 스냅샷) · copySteps()(웹 /api/recipe용 단계 목록).

TemperatureSensor — 온도 측정

Core 0 전용 태스크에서 MAX31865를 1Hz 폴링(소프트웨어 SPI). 모터 코어에 영향 없음. fault는 즉시 clear하지 않고 연속 5회 누적 후에만 시도 → 단선/접촉불량을 UI에서 끊김 없이 관찰.

  • 결선 모드: 보드별 rtdWires(2/3/4) — 보드 솔더점퍼와 일치 필수.
  • 진단: 부팅 시 threshold 레지스터 SPI 라운드트립 자가진단(칩·통신 검증) + fault 비트 디코드 + raw RTD 출력.
  • 격리: rtdWires=0이면 init·폴링 태스크 미생성, MAX31865 핀도 건드리지 않음 → temperature()=TEMP_UNREAD(화면 --.-).
  • 오류 판정: 칩 fault 비트 + SW 플래그 — 0x01 SPI 미통신(raw 0x0000/0x7FFF), 0x02 유효범위(-20~100°C) 밖. 1초에 2°C 넘는 점프는 스파이크로 버리고 연속 3회면 수용.
  • 온도 계산: 측정저항 raw·RREF/32768 → 선형 보정 gain·R + offset → PT100 Callendar–Van Dusen 역산(뉴턴법). 보정은 NVS tcal(16장).

WifiManager — 네트워크

WebServer — HTTP

ESPAsyncWebServer 기반. HTML은 web_assets.h에 PROGMEM 임베드. 의존성(motion/recipe/temp/cmd/wifi/saver)을 begin()에서 주입받아 소유하지 않는다. /api/start는 요청별 버퍼(_tempObject)로 여러 기기가 동시에 보내도 본문이 섞이지 않는다. 레시피 저장은 동시 저장 차단·64KB 상한·쓰기 실패 감지·커밋 전 JSON 검증. 화면보호기 업로드는 파일핸들(_upFile)을 한 번 열고 청크마다 write만 한다.

7레시피 실행 흐름

레시피는 StepInfo 배열(name / speedRpm / durSec / rotIntSec)이다. 웹에서 시작하면 곧장 실행되지 않고 스테이징을 거친다.

[Core 0] 웹 POST /api/start     →  stage.stage(name, steps)   // 뮤텍스 버퍼 적재만
[Core 1] loop()                  →  stage.consume()            // 안전한 시점에 꺼냄
                                →  stopAll() + recipe.load()  // 기존 정지 후 0단계 실행

각 단계:  startStep(idx) → durSec 경과 → requestStepStop()
          → takeStepStopped() → waitConfirm → confirm() → 다음 단계
  • waitConfirm — 단계 사이에 약품 교체를 위해 사용자 확인을 기다린다. 웹 /api/confirm 또는 디스플레이 OK.
  • skipStep / gotoStep — 확인대기 여부와 무관하게 다음 단계(또는 지정 단계)로. 감속 정지 완료 후 목표 단계를 처음부터 가속 시작(_pendingStep). 웹 상태 탭 진행도 바에서 단계를 누르면 확인창 → /api/goto.
  • pauseToggle — 진행 중 일시정지(감속 정지)/재개. 경과시간 보정. 단계 전환 대기 중에는 무시.

9크래시 분석 & 방지

증상. 모터 회전 중 화면보호기 진입·이미지 업로드·삭제 시 간헐적 Guru Meditation Error: Cache disabled but cached memory region accessed (Core 1 panic, reset reason 4). 처음엔 브라운아웃으로 오진했으나 WiFi 미사용 중에도 발생 → panic 확정. 근본 원인은 아래(v4.6.3에서 확정).

근본 원인 (v4.6.3, UART 백트레이스로 확정)

LittleFS 읽기/쓰기·NVS 같은 플래시 연산은 순간 캐시를 끈다. 캐시가 꺼진 동안에는 플래시뿐 아니라 PSRAM도 읽을 수 없다. 그 창에 IRAM ISR이 PSRAM에 있는 데이터를 읽으면 패닉한다.

백트레이스 (2026-10-04, UART0 TTL 캡처)
Guru Meditation Error: Core 1 panic'ed (Cache disabled but cached memory region accessed)
spi_flash_op_block_func → shared_intr_isr → pcnt_intr_service
레지스터 A2 = 0x3d800908 (PSRAM) = p_pcnt_obj,  A8 = 0xbad00bad (캐시 OFF 읽기 표식)

충돌 시나리오
모터 회전 → FastAccelStepper(MCPWM/PCNT) PCNT ISR 계속 발생 (IRAM, Core 1)
          ↘ 그 순간 Core 0이 /recipes.json 읽기 (TFT "Run recipe" 진입 등, 캐시 OFF)
          → ISR이 PSRAM의 p_pcnt_obj 읽음 → Cache disabled panic (reset 4)

IDF 4.4 pcnt 드라이버가 p_pcnt_obj를 heap_caps_calloc(MALLOC_CAP_DEFAULT)로 할당하는데, 이 방식은 "4KB 미만은 내부 RAM" 규칙이 적용되지 않아 PSRAM에 놓일 수 있다. 예전에 "모터 EMI로 생긴 인코더 인터럽트"로 진단했던 증상도 실제로는 이 버그였을 가능성이 높다.

왜 PCNT 인코더로 안 바꿨나. 하드웨어 PCNT 카운터로 옮기면 ISR 자체를 없앨 수 있지만, FastAccelStepper가 ESP32-S3 스텝 생성에 PCNT(MCPWM_PCNT)를 점유한다. 인코더용 PCNT가 모터와 충돌해 둘 다 깨졌다 → 인터럽트 인코더 유지 + 게이팅으로 결론.
새 ISR/플래시op 추가 시 원칙. ① ISR은 IRAM-safe(IRAM_ATTR 함수 + DRAM_ATTR 데이터 + 레지스터 직접 접근, pins() 같은 플래시 함수 호출 금지). ② IRAM ISR이 쓰는 드라이버 객체가 PSRAM에 놓이지 않는지 확인. ③ LittleFS/NVS 쓰기는 모터 IDLE·레시피 비활성일 때만.
크래시 로그 받는 법. 패닉 출력은 UART0(GPIO43 TX/44 RX)과 USB 양쪽으로 나간다. USB 시리얼은 포트를 닫으면 보드가 리셋되므로, USB-TTL 어댑터를 TX/RX/GND만 연결(VCC 연결 금지, 3.3V 레벨)해 DTR/RTS를 끈 채 녹화하는 게 안전하다. 백트레이스는 같은 버전의 firmware.elf로 xtensa-esp32s3-elf-addr2line -pfiaC -e firmware.elf 주소…. 코어덤프 파티션은 없다(파티션 변경 시 LittleFS가 지워지므로 보류).

13안전 설계 (물리 손상 방지)

  • 부팅 즉시 TMC2209 EN=HIGH — 리셋~setup 구간 floating으로 코일이 통전된 채 정지하면 발열/소손. 권장 HW 풀업: EN→3.3V 10K.
  • 부팅 즉시 패널 신호 핀 idle 고정 — floating noise가 패널 컨트롤러를 비정상 state로 몰아 ESD/latch-up 손상 누적 방지. 권장 HW 풀업: TFT CS·RST→3.3V 10K.
  • 디스플레이 배선 주의 — 신호선을 5V(VBUS) 근처로 라우팅하지 말 것. 5V가 신호핀에 닿으면 내부 ESD 다이오드를 통해 VCC 레일로 역주입되어 컨트롤러/백라이트가 손상될 수 있음 (실손상 사례 있음).
  • 탈조·충격 방지 — 모든 시작/정지/방향전환과 일시정지·단계 이동·건너뛰기는 S-커브 감속 경유. 비상정지(stopImmediate)만 즉시 정지. 비상정지 시 큐·대기 레시피를 폐기해 정지 직후 재기동 방지.
  • 노이즈 가드 — 인코더/버튼 노이즈 버스트 → 패널 입력 3초 차단, 60초 내 3회 → 모터 정지(레시피는 일시정지). 연속 비정상 리셋(브라운아웃·패닉·WDT) 3회 → 모터 잠금(전원 재투입 해제), 웹·TFT에 LOCKED.
  • 운전 중 플래시 쓰기·재부팅 금지 — 9장·10장.
  • 정전·리셋 복구 — 재부팅 후 모터 자동 구동 없음. 웹 배너/TFT RESUME?에서 이어서·단계 처음부터·다음 단계·취소. 정전 시 경과는 마지막 REST 기준 근사.
  • 하드웨어 감시 (HwSafety, 배선 시) — DIAG HIGH 60ms → 코일 즉시 차단, 구동 중 VM<10.5V 0.5초 → 정지, VM>28V → 즉시 차단. 레시피 일시정지 보존 + 모터 잠금, 원인 해소 후 웹에서 해제. 배선: DIAG→GPIO + 10kΩ 풀다운, VM—100kΩ—ADC1(1~10)—10kΩ—GND + 100nF, PinMap.h에 diagPin/vmPin/vmRatio.
  • 냉각 — 75RPM 연속 2h+ 시 모터·전자부 ≈50°C(실측). 발열은 I²R 지배 → VREF 최소 유지 정책.
  • 전원 — 소비는 1A 미만(추정)이라 20V 1.5A 이상이면 충분. 20V 라인에 퓨즈(1.5~2A), 드라이버 VM 근처 100~470µF, 5V 레귤레이터 출력에 쇼트키 다이오드(USB 5V가 레귤레이터를 거쳐 20V 라인으로 역류하는 것 방지) 권장. USB만 꽂은 채 모터를 돌리지 말 것, 전원 켠 채 모터 커넥터 탈착 금지.

AP SSID를 mDNS 이름으로 쓴다 → http://이름.local. 새 SSID는 규칙(영문 소문자·숫자·-, 1~32자, 하이픈 시작·끝 금지)을 웹이 입력 중 변환하고 서버가 검증(위반 400). 기존 규칙 밖 SSID는 유지하고 이름만 변환한다(바꾸면 슬레이브·폰의 저장된 연결이 끊기므로).

마스터의 자체 DNS(Core 0 태스크)가 자기 이름은 AP IP로, 연결된 다른 보드 이름은 mDNS로 찾아 대리 응답(60초 캐시)한다 — .local을 못 푸는 안드로이드도 이름으로 연다. 그 외 도메인은 NXDOMAIN. 윈도우는 mDNS를 먼저 시도해 첫 접속이 3~4초 걸릴 수 있다.

보드 번호 (웹 설정, 1~9)

AP 대역 192.168.(3+N).1을 정한다(1번=4.1, 2번=5.1).

AP 대역을 나눈 이유: 다른 보드의 AP에 STA로 붙을 때 자기 AP와 같은 대역이면 라우팅이 깨진다. AP 최대 동시 접속은 10(폰 여러 대 + 다른 보드가 함께 사용).

여러 대 동시 제어 (기존 제어 화면)

폰 ──WiFi──► 마스터(바디2) AP  ◄──STA(DHCP)── 슬레이브(바디1 …)
             └ 마스터 웹 → 상태 탭 "🔗 동시 제어" ON
                → /api/peers (AP 접속 기기 IP) → 각 IP /api/status로 보드만 골라 자동 발견
  1. 보드마다 서로 다른 보드 번호·AP 이름.
  2. 슬레이브: 설정 → 홈 WiFi [검색] → 마스터 AP 선택 → 비밀번호 → 저장. 고정 IP 불필요(옵션 자체 제거).
  3. 폰은 마스터 AP에만 접속 → 상태 탭 🔗 동시 제어 켜기 → 보드 자동 발견(MAC으로 기억, IP가 바뀌어도 유지). 체크 해제로 제외.
  4. 이 화면의 시작·정지(재시도)·안전정지·일시정지·다음 단계·건너뛰기·진행도 바 단계 이동·수동 운전이 선택된 보드 전체에 전달된다. 일시정지는 보드별 상태에 맞춰(멈출 보드만 / 재개할 보드만), 다음 단계는 확인대기 보드에만, 단계 이동은 그 단계가 있는 보드에만 → 상태 엇갈림 방지. 실패 보드는 알림.

보드 간 통신은 없어서 한 대가 꺼져도 나머지는 계속 동작한다. 레시피 타이밍은 각 보드가 자체로 재므로 시작 시각 차이(수십 ms)는 결과에 영향 없다. 실측: 바디1 자동 발견, 정지 전달 14ms. 모든 보드가 집 공유기에 함께 붙은 구성은 자동 탐색 대상이 아니므로 /multi(IP 수동 입력)를 쓴다.

WiFi 검색 / 진단

  • 설정 → 집 WiFi 이름 옆 검색: 2~4초 비동기 검색, 신호 막대·dBm·채널·개방망 표시, 고르면 이름 칸 자동 입력. 검색 중 AP 클라이언트 통신이 잠깐 느려질 수 있다.
  • 디바이스 정보·멀티 카드에 RSSI(STA 수신 세기) 표시 — 배치 비교용.
실측 사례 (바디1). 같은 펌웨어인데 바디1만 큰 응답이 8초 타임아웃·ping 손실 15%, WiFi 검색에서 같은 AP를 약 15dB 약하게 수신. 강한 신호(-37dBm)에서만 정상 → 수신 감도 저하(안테나 가림·-1U 외부안테나 누락·전원 노이즈 의심). 임시로 바디2 AP에 STA로 붙여 운용.

플래시 용량·PSRAM 종류는 빌드 타임 설정이라 사양마다 바이너리가 다르다. 핀·화면·온도센서는 런타임(PinMap.h)이라 같은 사양 안에서는 .bin 하나로 모든 보드를 지원한다.

웹 OTA

  1. 웹 설정 → 펌웨어 업데이트 → firmware.bin 선택 → 업로드(진행률 표시) → 자동 재부팅. 레시피·설정 유지.
  2. 거부 조건: X-OTA 헤더 없음(외부 페이지 CSRF 차단) · 모터/레시피 동작 중 · 다른 기기가 업로드 중(10초 무응답이면 끊긴 업로드로 정리) · 이미지 헤더의 플래시 용량이 보드와 다름(wrong board variant).
  3. 자동 롤백: OTA 성공 시 NVS ota/pending 표시. 새 펌웨어가 연속 비정상 리셋 3회(가드 잠금)면 이전 파티션으로 되돌리고, 60초 정상 가동(모터 정지 상태)하면 확정한다. 펌웨어는 살아 있지만 WiFi가 안 뜨는 경우는 롤백되지 않으므로 USB로 복구.
구형 보드 이전 (바디2 사례). v2.2(Arduino 기본 파티션, 앱 1.25MB)는 v4.x(약 1.5MB)가 들어가지 않아 OTA 불가 → ① esptool read_flash로 8MB 전체 백업 + verify_flash 대조, ② 백업에서 LittleFS의 최신 recipes.json 추출, ③ pio run -e n8r2 -t upload(파티션 표 교체), ④ 웹으로 레시피 복원. 백업은 backups/.

16온도 보정

측정저항에 직선 보정을 건다: R_cal = gain · R_meas + offset(Ω) → PT100 표준식으로 온도 계산. RREF 오차·PT100 공차·2선식 리드선 저항(오프셋)·보드 결선 왜곡(기울기)을 함께 흡수한다. 값은 보드별 NVS tcal, 허용 범위 gain 0.85~1.15 / offset ±20Ω.

웹 절차 (설정 → 온도 보정)

  1. 센서와 기준 온도계를 같은 물에 나란히 5cm 이상 담그고 저으면서 1~2분 안정.
  2. 기준 온도 입력 → [점 기록] (5초 평균, 0.2°C 이상 흔들리면 거부).
  3. 두 번째 점(10°C 이상 차이) 기록 → [보정 저장] → gain/offset 확인창. 1점만 기록하면 오프셋만 보정.
  4. 권장 점: 0°C 얼음물(잘게 부순 얼음 가득 + 물 조금, 2~3분) + 작업 온도 38°C. C-41(±0.15°C)은 기준 온도계 정확도가 결과를 좌우한다.

기록 중인 점은 브라우저에 보관(새로고침 유지). [마지막 점 삭제]·[점 지우기]·[보정 초기화]. 실패 시 사유 표시.

보정이 유효한 조건. 센서·케이블·단자·보드 점퍼를 바꾸지 않을 것. 단자 접촉 저항 0.1Ω 변화 = 약 0.26°C. 센서 내부로 물이 스며든 누설은 시간에 따라 변해서 보정이 유지되지 않는다 — 보정 전에 선과 프로브 외피 사이 절연(MΩ 이상)을 확인.
실측 사례 (바디2, 미해결). 3선 결선 + 2선 모드에서 얼음물은 -0.44°C로 맞지만 31~38°C에서 2.5~3°C 낮음(기울기 -7.6%). 3선 모드는 RTD=0(fault 0x41). 보드 점퍼(3선)↔펌웨어(2선) 불일치·누설·비표준 센서 중 무엇인지 멀티미터로 확인 후 보정 예정(ISSUES.md F8).
